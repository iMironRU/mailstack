# mailstack

Развёртывание и обслуживание почтового стека на одном VPS:

- **[Poste.io](https://poste.io/)** — Postfix + Dovecot + Rspamd + Roundcube (ClamAV отключён ради экономии RAM)
- **Nginx Proxy Manager** — reverse-proxy, держит 80/443, выпускает сертификаты Let's Encrypt
- **Portainer CE** — управление Docker через веб
- **Uptime Kuma** — мониторинг доступности
- **go-autoconfig** — автонастройка почтовых клиентов (Thunderbird / Outlook / Apple Mail)

Резервное копирование — restic в S3, с веб-интерфейсом Backrest поверх.

## Быстрый старт

Проверить, годится ли машина под стек, — ничего не устанавливая и не меняя:

```bash
curl -fsSL https://raw.githubusercontent.com/iMironRU/mailstack/main/mailstack.sh | bash -s -- preflight
```

Проверить уже развёрнутый стенд снаружи, со своей рабочей машины:

```bash
./mailstack.sh doctor --external --host mail.example.com --domain example.com
```

## Что проверяет `preflight`

Скрипт отказывается устанавливать стек, если машина не годится, — вместо того чтобы упасть на середине установки.

**Блокирует:** не root; неподдерживаемый дистрибутив или архитектура; OpenVZ/LXC вместо полноценной виртуализации; нехватка RAM или места на диске; незавершённый `dpkg`; **занятые порты стека**; **конфликтующие пакеты на хосте** (postfix, exim4, dovecot, apache2, nginx — самая частая причина, по которой Poste.io не стартует); недоступность репозиториев Docker.

**Предупреждает:** отсутствие swap; заблокированный провайдером исходящий порт 25; отсутствующий или несовпадающий PTR; hostname не в виде FQDN; рассинхронизация времени по NTP; наличие IPv6 без AAAA/PTR; присутствие IP в блоклистах.

## Проверка репутации IP

`preflight` и `doctor` проверяют внешний IP по 10 зонам: Spamhaus ZEN, SpamCop, PSBL, Barracuda, Mailspike, s5h, CBL, UCEPROTECT 1/2/3.

Две детали, которые часто реализуют неправильно:

- **Spamhaus отказывает публичным резолверам.** Запрос через 8.8.8.8 или 1.1.1.1 возвращает `127.255.255.252` — это отказ в обслуживании, а не листинг. Наивная проверка засчитает его как «IP в чёрном списке». Скрипт различает эти случаи и сообщает о них по-разному.
- **`dnsbl.sorbs.net` исключён намеренно** — сервис отключён в 2024 году, зона всегда отвечает «чисто» и создаёт ложное ощущение покрытия.

## Проверка снаружи

Часть проблем принципиально не видна с самого сервера: локальный `ss` покажет `LISTEN`, даже если провайдер режет порт на своём фильтре. Поэтому `doctor --external` запускается **с рабочей машины**, а не с сервера, и проверяет:

- реальную доступность 25, 80, 443, 465, 587, 993, 995 из интернета;
- что порты админок (81, 9000, 9443, 3001) **не** открыты наружу;
- SMTP-баннеры и совпадение HELO-имени с PTR;
- срок и валидность TLS-сертификата;
- A / MX / SPF / DKIM / DMARC домена.

Совместим с bash 3.2, то есть работает на macOS из коробки.

## Потребление памяти

Замер на реальном стенде (2 vCPU / 1967 MB RAM), сразу после `deploy`:

Итого с системой — 1017 MB из 1967, свободно 950 MB, swap задействован на 16 MB. Отключение ClamAV решающее: он один занимает больше, чем весь остальной стек.

## Откат

Стенд рассчитан на многократную пересборку, поэтому установка обратима без пересоздания виртуальной машины.

```bash
mailstack.sh uninstall           # снести стек: контейнеры, тома, каталог
mailstack.sh uninstall --purge   # плюс откатить системные изменения
```

Чтобы откат был честным, `bootstrap` первым делом снимает состояние машины **до** любых изменений: исходный hostname, был ли уже установлен Docker, был ли swap, включал ли кто-то ufw раньше. Без такого снимка откат превращается в гадание — непонятно, на какое имя возвращать hostname и чей Docker сносить.

`--purge` откатывает **только то, чего на машине не было до нас**. Чужой Docker, ранее включённый ufw и заранее настроенный fail2ban остаются нетронутыми. Если в Docker есть посторонние контейнеры, он не удаляется вовсе — вместо этого выводится предупреждение.

Что не откатывается: `apt upgrade` и общесистемные пакеты (`curl`, `jq`, `dnsutils`, `whois`) — они безобидны и могут понадобиться другим задачам.

### Восстановление — слияние, а не замена

`restic restore` возвращает файлы из снимка, но **не удаляет те, которых в снимке нет**. При откате «грязной» системы остаётся мусор от прежнего состояния — удалённый ящик может частично воскреснуть. Штатный флаг `--delete` появился только в restic 0.17, а в Ubuntu 24.04 приезжает 0.16, поэтому:

```bash
mailstack.sh restore           # слияние: вернуть файлы из снимка поверх текущих
mailstack.sh restore --clean   # точный откат: очистить тома, затем восстановить
```

`--clean` чистит строго содержимое известных путей и только после проверки по шаблону. Пароль репозитория лежит внутри очищаемого каталога, поэтому сохраняется и возвращается обратно — иначе после очистки было бы нечем расшифровать снимок.

`--keep-env` сохраняет `.env` в `/root/mailstack.env.saved`, чтобы при повторной установке не вводить креды релея заново.

## Резервное копирование

Бэкап **не блокирует развёртывание**: `deploy` работает без него и только предупреждает, а настроить хранилище можно в любой момент командой `backup setup`.

Движок — restic: шифрование на стороне клиента, дедупликация, политики хранения. Поддерживаемые бэкенды:

| Вариант | Когда подходит |
|---|---|
| **SFTP** | Есть вторая машина. Нативно, по ssh, без лишних слоёв. Заодно готовая площадка для `migrate` |
| **Локальный каталог** | Примонтированный диск или сетевая шара. Быстро, но не переживёт потерю сервера |
| **S3** | Selectel Object Storage, Backblaze B2, MinIO, Yandex |
| **rclone** | Всё остальное: FTP, WebDAV, Яндекс.Диск, Google Drive |

Две детали, которые стоит знать заранее:

- **Нативной поддержки FTP у restic нет** — только через rclone. Работает, но FTP не шифрует канал, не даёт атомарности операций и заметно медленнее на больших репозиториях. Если задача — «складывать файлы на другой сервер», SFTP решает её лучше и нативно.
- **Backblaze B2 подключать через S3-совместимый API**, а не через нативный бэкенд `b2:` — [так рекомендуют сами разработчики restic](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html) из-за проблем с обработкой ошибок в используемой библиотеке.

Веб-интерфейс — [Backrest](https://github.com/garethgeorge/backrest) поверх restic. Важно, что это именно обёртка: репозиторий остаётся в родном формате restic и читается голым CLI с любой машины. Поэтому `backup`, `restore` и `migrate` работают напрямую через restic, а Backrest ставится только как смотровое окно — доступ к данным не должен зависеть от работоспособности ещё одного сервиса.

## Автономная отправка без релея

Релей — временная подпорка на время блокировки 25-го порта, а не часть архитектуры. Приём почты автономен всегда: чужие серверы доставляют на входящий 25, и он от провайдерских блокировок обычно не страдает. Автономной отправке нужно следующее.

**Исходящий 25 у провайдера.** Единственное условие, которое нельзя настроить на своей стороне:

| Провайдер | Исходящий 25 |
|---|---|
| Hetzner, OVH | открыт по умолчанию |
| Contabo | открыт, лимит ~25 писем/мин |
| Selectel | закрыт, разблокировка по тикету — обычная процедура |
| DigitalOcean, Vultr | закрыт, разблокировка не гарантируется |
| AWS, Azure, GCP | закрыт без возможности снятия |

**PTR, совпадающий с HELO.** Задаёт только провайдер. Проверяется командой `doctor`, включая forward-confirmed rDNS.

**SPF, DKIM и DMARC** — все три. С 2024 года Gmail и Yahoo требуют их от любого отправителя, а не только от массовых рассылок.

**Валидный TLS** на 25, 465, 587 и 993 — этим занимается `certs-sync`.

**Репутация IP** нарабатывается временем, а не конфигурацией. Свежий адрес подозрителен по умолчанию: первые недели письма могут уходить в спам при полностью корректных настройках. Прогрев — начинать с десятка писем в день и наращивать постепенно; резкий старт с большого объёма отправляет в фильтры надёжнее любой ошибки в DNS. Microsoft (Outlook.com, Hotmail) режет новые адреса агрессивнее остальных, и разблокировки там иногда приходится добиваться через их форму для отправителей.

**Мониторинг блоклистов** — попадание в Spamhaus нужно замечать в тот же день. Это `doctor`, а для доступности — Uptime Kuma.

Профиль «несколько доменов, десятки писем в день живым адресатам, которые отвечают» для автономной отправки подходит хорошо: ответы и отсутствие жалоб — лучший сигнал репутации. Массовые рассылки — отдельная задача, и там специализированный сервис обычно оправдан.

## SMTP-релей

Многие провайдеры блокируют исходящий порт 25. Сервер при этом принимает почту, но не может доставлять её напрямую. `bootstrap` определяет блокировку сам и предлагает настроить релей — шаг необязательный, к нему можно вернуться позже.

Правильное решение — тикет провайдеру на разблокировку 25. На время ожидания подойдёт релей по порту 587: собственный другой почтовый сервер либо публичный сервис.

Проверить креды релея до развёртывания:

```bash
./mailstack.sh relay-test --host smtp-relay.brevo.com --user xxxxx@smtp-brevo.com
```

Пароль запрашивается интерактивно и не принимается аргументом — иначе он остался бы в истории командной строки и был бы виден в `ps`. Проверяются соединение, STARTTLS и собственно аутентификация. Без такой проверки ошибка в кредах обнаруживается только по молчащей очереди Postfix: письма принимаются, ставятся в очередь и тихо копятся.

У Brevo есть allowlist IP: при первом использовании ключа адрес авторизуется автоматически, но если за 30 дней новых адресов не появилось, блокировка неизвестных IP включается сама. Это стреляет при миграции — на новой машине те же креды перестают приниматься, хотя почтовый сервер настроен верно. Новый IP нужно добавить в Security → Authorized IPs **до** переключения.

Актуальные бесплатные тарифы (2026): **Brevo** — 300 писем/сутки бессрочно, **Mailjet** — 200/сутки, **Resend** — 3000/месяц. У SendGrid бессрочный free-план убран в 2025 году, Amazon SES закрыл free tier для новых клиентов в июле 2026.

## Требования

Сервер: Ubuntu 22.04/24.04 или Debian 12/13, x86_64 или arm64, от 2 GB RAM (RAM + swap), от 10 GB свободного диска, полноценная виртуализация (KVM).

Рабочая машина для `--external`: bash, python3, dig.
